# 04 — Топология Баз Данных, Контрактов и Межсервисного Взаимодействия

> **Проект:** «Бюджетный нутрициолог»
> **Архитектурный стандарт:** Offline-First Client (Room KMP) · gRPC / Protobuf · Event-Driven Microservices (Spring Boot 4, PostgreSQL 17, Kafka 3.9 / Avro, Redis 7).

---

## 1. Область действия

Это целевая архитектура, а не перечень готовых функций. На HEAD 83f9352 существуют Profile Proto, мобильный кэш профиля и две Avro-схемы; серверные master-changelog пусты, Diary/Catalog/Recipe API и синхронизация избранного ещё не реализованы.

Мобильный клиент — место расчёта порций и пользовательских остатков; Room — источник данных UI, включая неподтверждённые изменения. Сервер хранит синхронизированные записи и даёт доступ с других устройств. Сетевые операции идут через Envoy Gateway, не напрямую в Kafka.

```text
Каталог цен -> Room -> расчёт порции и остатка в mobile/shared
                          |                         |
                          v                         v
                 Diary.AddEntry             Recipe AI: контекст запроса
                 снимок + ключ              лимиты, исключения, избранное
                          |
                          v
                    diary_db + Outbox

Room favorite_operations -> Catalog.SetFavorite -> catalog_db
Profile.GetProfile/UpdateProfile <-> профиль и недельный лимит
```

## 2. Владельцы данных

| Данные | Владелец и хранение | Правила |
|---|---|---|
| Биометрия, цели, недельный лимит | Profile / profile_db; локальный кэш profiles | Клиент изменяет через существующий Profile API |
| Справочные продукты и цены | Catalog / catalog_db; мобильный кэш | Текущие предложения; не исторические расходы |
| Рецепты и дневные шаблоны | Catalog: recipes, recipe_ingredients, meal_plan_templates, meal_plan_items | AI-ответ не становится объектом каталога автоматически |
| Избранное | Catalog: user_favorite_foods, user_favorite_recipes, user_favorite_meal_plans | UNIQUE(user_id, FK); SetFavorite для FOOD_ITEM/RECIPE/DAILY_MEAL_PLAN |
| Локальные намерения избранного | Room: favorite_items + favorite_operations | Устойчивый FIFO на аккаунт, tombstone, ключ на операцию |
| Запись питания и стоимость порции | Room до отправки; Diary / diary_db после ACK | Сервер сохраняет клиентский снимок, не пересчитывает сумму |
| Остаток бюджета/КБЖУ | Производное значение mobile/shared | Профиль + полная локальная история периода; отдельного серверного счёта нет |
| Контекст AI | Один запрос генерации | Готовые ограничения и предпочтения, без событийного денежного баланса |
| Результат CV | Будущий food-cv-service / кэш Redis | Распознавание, не источник фактического расхода |

Канонические поля и примеры: [Profile](../../backend/profile-service/README.md), [Catalog](../../backend/catalog-price-service/README.md), [Diary](../../backend/diary-service/README.md), [Recipe AI](../../backend/recipe-ai-service/README.md), [Mobile](../../mobile/README.md).

Для дневного меню каталог владеет `meal_plan_templates(id, name, target_calories, estimated_price, is_active, created_at)` и `meal_plan_items(id, meal_plan_id, recipe_id, meal_type)`. Избранное связывается с шаблоном каталога, а не с временным результатом генерации.

### 2.1 Избранное и восстановление

Единый проект API — `SetFavorite(target, is_favorite)` и `ListFavorites`, определённый в Catalog README. Субъект берётся из авторизации. Сервер атомарно сохраняет изменение и результат дедупликации; Redis не является единственным хранилищем ключей.

Room сохраняет желаемое состояние и неизменяемую операцию в одной транзакции. Удаление — операция false и tombstone до ACK. Последовательность добавить→удалить→добавить доставляется FIFO; старый ACK удаляет только свою операцию, не перезаписывает новое намерение. После исчерпания попыток операция остаётся на диске. Полные переходы, правила повторов/отмены/смены аккаунта и пример worker — [Mobile Stack §3](03-mobile-stack.md#3-offline-first-дневник-и-избранное).

Событие user.favorite.changed не требуется: текущие локальные предпочтения передаются в запрос AI. Это также учитывает ещё не синхронизированные нажатия.

## 3. Стоимость, бюджет и события

### 3.1 Почему расчёт остаётся на мобильном устройстве

Ранее предполагалось вести остаток бюджета в Recipe AI по событиям дневника. Это требовало серверного расчёта стоимости и дополнительной проекции расходов, хотя CaloriesConsumedEvent не содержит денег. Для текущего интерактивного сценария такая проекция не нужна: клиент уже знает выбранные цены, количество и локальные PENDING-записи.

Принято: доменный слой mobile/shared рассчитывает порцию и остатки; сервер сохраняет присланный снимок, проверяет владельца, формат, диапазоны и идемпотентность. Повторного умножения цены на количество в Diary нет. Проект не принимает платежи: сохранённая стоимость — пользовательская оценка потребления, а не проверенный кассовый чек.

### 3.2 Минимальный снимок и история

- В записи остаются количество, нутриенты, время, итоговая сумма в копейках и валюта RUB. Исходная выбранная цена и база количества сохраняются, если известны; они нужны для объяснения расчёта и осознанного редактирования, а не повторной оценки на сервере.
- Для MVP серверная колонка `price NUMERIC(10,2)` хранит присланные копейки с точным переводом представления; RUB фиксирована. Неизвестная сумма — null, известный ноль — 0. Схема и ограничения определены в Diary README.
- Включать историю всех цен каталога в каждую запись не нужно. Обновление каталога меняет только будущую оценку. Сохранённый расход не переписывается автоматически.
- Клиент считает сумму каждой порции один раз с HALF_UP до копейки, затем складывает сохранённые итоги. Деньги не рассчитываются в Double; правило массы и округления — Mobile Stack §3.1.
- Сервер хранит историю для восстановления после переустановки и синхронизации устройств. Возможная аналитика может агрегировать сохранённые суммы; она не требует заново оценивать продукты по актуальному каталогу.
- Бюджет профиля — пользовательский недельный лимит в RUB; остаток — лимит минус сумма записей периода, рассчитанная клиентом. Для периода используется выбранный IANA часовой пояс; недели начинаются в понедельник. MVP применяет текущий лимит к отображаемой неделе, не обещает историю прошлых настроек бюджета. Исторические суммы записей при изменении лимита не меняются.
- Профиль пока передаёт weekly_budget как double в существующем Proto. Мобильный адаптер валидирует конечность, диапазон и точность до копейки и переводит значение в целые копейки до расчётов. Действующий контракт ради этого документа не меняется.

### 3.3 Что получает Recipe AI

Клиент передаёт доступные КБЖУ, выделенный денежный предел для блюда/дня, исключения и ID локальных предпочтений. Recipe AI не вычитает расходы из Kafka и не хранит денежный остаток пользователя в Redis. Полная история расходов для генерации ему не нужна.

AI может оценивать будущие варианты по данным каталога, чтобы подобрать их под предел. Такая оценка предложения не является фактическим расходом: выбранную порцию клиент считает по своим выбранным ценам, показывает пользователю и сохраняет. Новые серверные RPC для расчёта суммы не вводятся.

При неполном локальном кэше недели или неизвестных ценах остаток помечается как приблизительный; пользователь задаёт предел генерации явно. Одновременные офлайн-записи другого устройства станут доступны после синхронизации — глобально актуальный остаток офлайн не гарантируется.

### 3.4 Совместимость событий

Существующие UserRegisteredEvent и CaloriesConsumedEvent сохраняются. Регистрация не подменяет обновление профиля, событие калорий не содержит и не должно автоматически получать стоимость. Отдельные события обновления профиля и избранного не вводятся без потребителя. Матрица назначений и канонические ссылки — [Backend Stack §4](02-backend-stack.md#4-kafka--avro--schema-registry).

## 4. Анализ альтернативных вариантов и обоснование выбора

### Альтернатива 1: «Всё на мобильном устройстве (Local-Only SQLite, без сервера)»
* **Суть:** Приложение считает всё в Room и никуда ничего не отправляет.
* **Почему не подходит для «Бюджетного нутрициолога»:**
  1. **Потеря данных:** При удалении приложения, смене телефона или сбросе кэша пользователь навсегда теряет историю питания за недели и месяцы.
  2. **Невозможность работы ИИ-нутрициолога:** На смартфоне невозможно локально запускать тяжёлые LLM и держать парсер актуальных цен всех супермаркетов. Для подбора ужина под оставшиеся 500 ккал и 200 ₽ достаточно переданного клиентом контекста; хранение истории на сервере нужно для восстановления и синхронизации.
  3. **Нет мультидевайса:** Невозможно переключиться между телефоном, планшетом или веб-версией.

### Альтернатива 2: «Монолитный бэкенд с единой базой данных»
* **Суть:** Все таблицы (`profiles`, `diary`, `catalog`, `recipes`) в одной схеме монолитного Spring Boot приложения.
* **Почему уступает:**
  1. **Взаимная блокировка ресурсов:** Тяжёлые вызовы генерации рецептов через Gemini LLM или обработка картинок Computer Vision вызывают нехватку потоков/соединений и «вешают» быстрые операции записи дневника и авторизации.
  2. **Размытие границ ответственности:** Разработчики начинают делать кросс-доменные прямые `JOIN` между каталогом цен и личным профилем, превращая код в спагетти.
  3. **Невозможность независимого масштабирования:** Сервис дневника требует быстрого масштабирования по I/O записи, а AI-сервис — по CPU/памяти и числу асинхронных вызовов к внешним API.

### Альтернатива 3: «Классический REST + JSON over HTTP/1.1»
* **Суть:** REST-эндпоинты вместо gRPC, JSON вместо Protobuf/Avro.
* **Почему уступает:**
  1. **Оверхед по трафику и парсингу:** Текстовый JSON в разы тяжелее компактного бинарного Protobuf. Для мобильного приложения на нестабильном мобильном интернете gRPC по HTTP/2 даёт колоссальный выигрыш в скорости и энергопотреблении.
  2. **Отсутствие строгого типизированного контракта:** В REST изменения структуры DTO легко ломают клиент в рантайме. В gRPC/Buf строгий контроль обратной совместимости (`buf breaking`) гарантирует целостность API ещё на этапе сборки в CI.

### Альтернатива 4: «Хранение избранного в profile-service и отправка напрямую с клиента через Kafka»
* **Суть:** Добавить таблицу `favorite_recipes` в `profile-service`, а мобильный клиент при добавлении в избранное отправляет сообщение напрямую в топик Kafka.
* **Почему это антипаттерн и категорически отвергнуто:**
  1. **Нарушение Bounded Contexts (DDD):** `profile-service` управляет биометрией (рост, вес, цели КБЖУ, бюджет). Рецепты, продукты и меню принадлежат домену `catalog-price-service`. Если положить избранное в профиль, `profile-service` не сможет обогатить список данными (название, КБЖУ, ингредиенты, актуальные цены), что приведёт к N+1 сетевым запросам и размытию доменных зон.
  2. **Нарушение безопасности периметра (Zero-Trust):** Мобильные клиенты **никогда не пишут напрямую в Kafka-брокер**. Брокер находится внутри защищённого контура Kubernetes. Открытие портов Kafka в интернет ломает аудит, JWT-валидацию на Envoy Gateway и открывает вектор DDoS-атак.
  3. **Отсутствие синхронного подтверждения (ACK/Error):** Прямая запись в Kafka не даёт клиенту валидации (существует ли рецепт, не удалён ли он).
  4. **Правильное решение:** Мобильный клиент вызывает `SetFavorite` через Envoy Gateway. Каталог сохраняет желаемое состояние и запись дедупликации в одной транзакции. Для текущей персонализации AI клиент передаёт локальные предпочтения в запросе, отдельная Kafka-проекция не нужна.

### Почему наш выбор — лучший (Offline-First + Microservices + gRPC + Outbox):
1. **Максимальная отзывчивость для пользователя:** Ввод приёмов пищи обновляет локальную Room без ожидания сети.
2. **Гарантированная надёжность доставки:** Устойчивая очередь и ключи позволяют повторять отправку после сбоев; для событий Outbox требует дедупликации потребителем. Блокировки и ошибки остаются видимыми, автоматические попытки ограничены.
3. **Безопасность и масштабируемость:** Envoy Gateway валидирует токены OAuth 2.1 PKCE на периметре сети, разгружая сервисы от криптографических проверок.
4. **Умный ИИ-ассистент:** Контекст мобильного клиента позволяет генерировать меню под доступные ему остатки КБЖУ и бюджета, включая ещё не отправленные записи.
